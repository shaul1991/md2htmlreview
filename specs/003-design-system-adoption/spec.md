# Feature Specification: 디자인 시스템 도입 — 데스크톱 3-pane 리뷰 워크스페이스

**Feature Branch**: `003-design-system-adoption`

**Created**: 2026-06-01

**Status**: Draft

**Input**: User description: "design/ 의 디자인 시스템과 UI/UX 를 현재 프로젝트에 적용한다. 데스크톱 3-pane 전면 재설계, vanilla-ts 유지, 모바일은 후속."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 3-pane 워크스페이스에서 plan 검수 시작 (Priority: P1)

리뷰어가 앱을 열면, 빈 상태에서는 시작 방법을 안내하는 온보딩 화면이 보인다. plan markdown 을
붙여넣고 변환하면, 화면이 `이력 | 섹션 | 노트` 세 패널로 구성된 워크스페이스로 바뀌고 섹션이
카드로 나열된다. 리뷰어는 한 화면에서 문서 이력·검수 대상·의견을 동시에 본다.

**Why this priority**: 이 레이아웃 전환이 이번 재설계의 본질이다. 이것만 구현해도 "단선형 → 3-pane"
이라는 핵심 가치가 전달되고, 나머지 스토리(섹션 조작·노트·핸드오프)가 얹힐 토대가 된다.

**Independent Test**: 빈 상태에서 온보딩이 보이는지 확인 → 샘플 plan 붙여넣기 → 변환 →
`이력/섹션/노트` 3개 패널과 섹션 카드 목록이 렌더되는지 확인.

**Acceptance Scenarios**:

1. **Given** 저장된 문서가 없는 첫 실행, **When** 앱을 연다, **Then** 시작 방법을 안내하는 온보딩 빈 상태가 보인다.
2. **Given** 온보딩/붙여넣기 상태, **When** plan markdown 을 붙여넣고 변환한다, **Then** 3-pane 워크스페이스로 전환되고 섹션들이 카드로 나열된다.
3. **Given** 이미 저장된 문서가 있는 재실행, **When** 앱을 연다, **Then** 마지막 활성 문서가 3-pane 으로 복원된다.

---

### User Story 2 - 섹션 탐색: 선택·접기·노트 보유 표시 (Priority: P2)

리뷰어가 긴 plan 을 검수할 때, 각 섹션 카드를 접거나 펼치고, 현재 보고 있는 섹션을 선택 상태로
구분하며, 의견이 달린 섹션을 한눈에 알아본다.

**Why this priority**: 섹션 수가 많아질수록 탐색 효율이 검수 품질을 좌우한다. P1 레이아웃 위에서
바로 가치를 더하지만, 레이아웃 없이는 성립하지 않으므로 P2.

**Independent Test**: 여러 섹션이 있는 문서에서 한 카드를 접었다 펴고, 한 섹션을 선택해 활성 표시를
확인하고, 노트가 달린 섹션이 시각적으로 구분되는지 확인.

**Acceptance Scenarios**:

1. **Given** 섹션 카드 목록, **When** 한 카드의 헤더를 토글한다, **Then** 본문이 접히거나 펼쳐진다.
2. **Given** 섹션 카드 목록, **When** 한 섹션을 선택한다, **Then** 그 카드가 활성 상태로 표시된다.
3. **Given** 일부 섹션에 노트가 있다, **When** 목록을 본다, **Then** 노트 보유 섹션이 시각적으로 구분된다.

---

### User Story 3 - 노트 패널에서 의견·반박 작성 (Priority: P2)

리뷰어가 노트 패널의 작성기로 선택한 섹션에 의견을 남기고, 기존 의견에 대한 반박을 스레드로
연결한다. 패널에는 섹션별 노트 수가 표시된다.

**Why this priority**: 의견·반박은 제품의 핵심 행위지만, 새 노트 패널 UI 위에서 동작해야 하므로
레이아웃(P1) 다음 단계. 기존 기능을 새 UI 로 옮기는 것이 본질이라 P2.

**Independent Test**: 섹션 선택 → 작성기로 의견 추가 → 그 의견에 반박 추가 → 스레드 연결과 섹션별
카운트가 맞는지 확인.

**Acceptance Scenarios**:

1. **Given** 한 섹션이 선택됨, **When** 작성기에 의견을 입력해 추가한다, **Then** 노트 패널에 해당 섹션 그룹으로 의견이 표시된다.
2. **Given** 기존 의견이 있다, **When** 그 의견에 반박을 추가한다, **Then** 반박이 대상 의견을 참조하는 스레드로 표시된다.
3. **Given** 섹션마다 노트 수가 다르다, **When** 패널을 본다, **Then** 섹션별 노트 수가 카운트로 표시된다.

---

### User Story 4 - 핸드오프 복사 (Priority: P3)

리뷰어가 검수를 마치면, 원본 + 섹션별 의견을 구조화한 텍스트를 클립보드로 복사해 agent workflow 로
되돌린다.

**Why this priority**: 기존에 동작하던 핸드오프를 새 UI 에서도 보존하는 것. 신규 가치가 아니라
회귀 방지 성격이라 P3.

**Independent Test**: 의견이 있는 문서에서 핸드오프 복사 → 클립보드 내용이 원본 + 섹션별 의견 형식인지 확인.

**Acceptance Scenarios**:

1. **Given** 의견이 달린 문서, **When** 핸드오프 복사를 실행한다, **Then** 원본 plan 과 섹션별 의견이 결합된 텍스트가 클립보드에 담긴다.

---

### Edge Cases

- 헤딩이 없는 plan: 단일 intro 섹션으로 처리되어 3-pane 에 정상 표시되는가?
- 빈/공백 입력 변환: 빈 상태 또는 안내가 유지되고 깨지지 않는가?
- 노트가 하나도 없는 섹션: 노트 보유 표시 없이 정상 렌더되는가?
- 매우 긴 단일 섹션/매우 많은 섹션: 패널 스크롤로 탐색 가능한가?
- 라이트/다크 시스템 설정 전환: 토큰 기반 색이 양쪽 모두 가독성 있게 적용되는가?
- 저장된 문서가 손상된 경우: 빈 상태로 복구되고 충돌하지 않는가?

## Requirements *(mandatory)*

### Functional Requirements

**레이아웃 · 진입**

- **FR-001**: 검수 화면은 `문서 이력(좌) | 섹션 목록(중앙) | 노트(우)` 의 3-pane 워크스페이스로 제시되어야 한다.
- **FR-002**: 상단에 제품 식별(브랜드)과 내비게이션 영역이 있어야 한다.
- **FR-003**: 저장된 문서가 없을 때, 앱은 시작 방법을 안내하는 온보딩 빈 상태를 보여야 한다.
- **FR-004**: 사용자는 markdown 을 붙여넣어 검수 가능한 문서로 변환할 수 있어야 한다.

**섹션**

- **FR-005**: 각 섹션은 헤딩 제목과 식별자를 가진 카드로 표시되어야 한다.
- **FR-006**: 사용자는 섹션 카드를 접거나 펼칠 수 있어야 한다.
- **FR-007**: 사용자가 한 섹션을 선택하면 그 섹션이 활성 상태로 시각적으로 구분되어야 한다.
- **FR-008**: 노트가 달린 섹션은 그렇지 않은 섹션과 시각적으로 구분되어야 한다.

**노트**

- **FR-009**: 사용자는 노트 패널의 작성기로 섹션에 의견을 추가할 수 있어야 한다.
- **FR-010**: 사용자는 기존 의견을 참조하는 반박을 스레드로 추가할 수 있어야 한다.
- **FR-011**: 노트 패널은 섹션별 노트 수를 표시해야 한다.

**보존(회귀 방지)**

- **FR-012**: 노트는 새로고침 후에도 유지되어야 한다(기존 영속 동작 보존).
- **FR-013**: 여러 문서가 이력으로 보관되고 선택해 전환할 수 있어야 한다(기존 동작 보존).
- **FR-014**: 사용자는 원본 + 섹션별 의견을 구조화한 핸드오프를 클립보드로 복사할 수 있어야 한다(기존 동작 보존).
- **FR-015**: 렌더된 markdown 은 원본의 raw HTML 을 실행하지 않아야 한다(기존 안전성 보존).

**비주얼**

- **FR-016**: UI 는 도입된 디자인 시스템의 토큰(색·타입·간격)을 따라야 하며, 라이트/다크 테마를 모두 지원해야 한다.

### Key Entities *(include if feature involves data)*

- **문서(Document)**: 검수 대상 plan 한 건. 원본 markdown, 제목, 생성/수정 시각, 소속 노트를 가짐. 이력에 보관됨.
- **섹션(Section)**: 문서를 헤딩 기준으로 나눈 검수 단위. 식별자, 표시용 제목, 원본 조각, 렌더된 본문을 가짐.
- **노트(Note)**: 한 섹션에 달린 의견. 종류(의견/반박)와, 반박인 경우 대상 의견 참조를 가짐.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 리뷰어가 plan 붙여넣기부터 특정 섹션에 첫 의견 작성까지를 3회 이하의 주요 조작으로 끝낼 수 있다.
- **SC-002**: 노트가 달린 섹션은 목록에서 100% 시각적으로 식별된다(달린 섹션 중 표시 누락 0건).
- **SC-003**: 기존 검수 기능(섹션별 의견, 반박, 다중 문서 이력, 클립보드 핸드오프, markdown 안전성)이 재설계 후에도 모두 동작한다(회귀 0건).
- **SC-004**: 데스크톱 검수 화면의 시각 결과가 design 프로토타입(`design/index.html` 프로토타입 탭)과 일치한다.
- **SC-005**: 섹션이 많은(예: 20개) plan 에서, 리뷰어가 노트 패널을 화면에서 잃지 않고 임의 섹션의 의견에 도달할 수 있다.

## Assumptions

- **데스크톱 전용(이번 사이클)**: 모바일 셸(앱바·하단탭·드로어·바텀시트)은 이 spec 범위 밖이며 후속 spec 으로 다룬다.
- **스택 유지**: 기존 vanilla-ts + Vite 스택을 유지한다. 디자인은 프레임워크 마이그레이션이 아니라 포팅으로 도입한다(구체 방법은 plan 단계).
- **코어 모듈 보존**: 기존 순수 모듈(파싱·노트·export·영속)의 동작은 보존하되, 섹션 카드 헤더 표시를 위해 섹션에 표시용 제목 개념이 추가될 수 있다.
- **런타임 스왑 제외**: 테마/밀도/악센트의 런타임 전환(Tweaks 패널), 모드 전환(분할/단일), 계정 sync, MCP 진입점은 이 spec 범위 밖이다. 라이트/다크는 시스템 설정을 따른다.
- **샘플 데이터**: design 에 내장된 한국어 샘플 plan 을 온보딩/데모에 활용할 수 있다.
